Code-level analysis of the stock dump. About 53k instructions were decoded with a custom C166 disassembler: 96 standard task entry points plus 78 additional ones, 114 map references and 92 calibration maps. Every map is tied to the function that reads it and to the variables on its axes. Below: how the firmware is organised, the calculation chains (fuel, boost, EGR, injection timing) and the full map list.

Corrections to common definitions

These points matter for Stage 1. Each one was checked against the code that reads the map, not inferred from the shape of the data.

0x3C3AA = 2100

The boost setpoint is clipped by a 2100 mbar constant. After all corrections, task 0x160C4 takes min(setpoint, [0x3C3AA]). Raising the boost map 0x3C496 alone does nothing above 2100 until this constant is raised. Next to it is the deviation check: underboost above +250 mbar or overboost above −150 mbar (parameters 0x3C3B4/0x3C3B6) sets a fault on path 0x1D.

0x3A308

This is the EGR air-mass setpoint, not injection timing. Titanium labels it “Phase of injection”, but the code says otherwise. The map output (C2E4) is read only by task 0x1EBB6, which compares it with the MAF air mass (C216) through a PI controller, inverts the output with a 100 % − x curve and, on deviation, sets path 0x1E, i.e. P0400 (flag 0x3AFEE). The area 0x3A440–0x3A4D2 is not read by any visible code; its purpose is unknown, do not write there.

0x3CD30

Not a boost limiter. The map (rpm × fuel, 20.3…33.2) feeds C214 → C252, a value sent over CAN to the VP44 pump together with the fuel quantity. It is the start-of-injection request. Do not treat it as a boost limiter.

0x3C8A2

Not a fuel limiter. This is the boost valve pilot duty (rpm × fuel, up to 65.00 %). It is added to the pressure PI controller in task 0x1F6B8.

0x3BB40 / 0x3BA70

The active limiters are “Injection at part throttle” and “Torque limiter 2”. The copies 0x3B55A (“Injection ext”) and 0x3B8EA (“Torque limiter 1”) are only blended in with a factor from curve 0x3B926, which is all zeros in stock, so these copies have no effect on fuelling. Edit the active pair.

How the code works

Tasks

All calculations are split into tasks called by the scheduler in ROM. 96 tasks begin with the standard prologue mov r0,[0040h]; sub r0,#frame; mov [r0],[FD86h], i.e. they allocate a frame on their own stack (stack tops at 0x3803C–0x38042). Another 78 entry points start directly with cmp r0,[FD86h]. Tasks exit via jmps 00:07B4, stack overflow goes to 00:0276. The task order table lives in ROM, so call order and rate cannot be recovered from the dump.

Task pattern

A task first copies the globals it needs into its work area (C0FA–C126, FC66–FC6A), computes, and writes the result to one or two globals. Intermediate values are mirrored into monitoring variables DCxx–DExx. Their addresses are what map headers store as “axis ID”, which is why the boost map Y axis is DD94 = C1EC + C1D0.

Maps

Header: [ID X][nx][X…][ID Y][ny][Y…][data]. Data is stored row by row along X: index = x·ny + y. The code fetches the map address from a pointer table, not directly. Example: mov r12,[100Ch] reads 0x3900C → 0x446E → map 0x3C46E. Then r13=X, r14=Y and calls 00:20D6, result in r4.

Faults

All faults are reported via calls 01:4002: r2 = (path<<8) | ~bit, r1 = pointer to an 8-byte debounce record. Each path has a header with its P-code and an enable flag. Example: path 0x1E → P0400, flag 0x3AFEE.

y = C1EC + C1D0. Base (rpm, y). At altitude (rpm, y) is added with weight (atm.): 100 % at 750 mbar and below, 0 % from 950 mbar. Then a temperature factor , a dynamic term via ROM 22F2, and an offset (zeros). The result is clamped to at least 0 and at most [0x3C3AA] = 2100.

0x1F6B8

Controller. Error = C224 − C220, fed to a P term (ROM 21A2) and an I term (21C4). The pilot (rpm, y) is added and the result is clamped to 0…65.00 % (0x3C3F2/0x3C3F6). PI controller in ROM 2430 (parameters 0x3A6AC, 0x3A6B6, 0x3A6C0) on the error C2E4 − C216. The output is inverted by curve (100 % − x). P-codes were read from the path headers in the calibration. Path 0x1E → P0400 → 0x3AFEE has been confirmed in practice. The other mappings were built the same way but not verified individually. For some paths (0x12/0x13, 0x24/0x25, 0x38–0x3D) the header could not be identified unambiguously.

What the dump does not contain

  • The scheduler and task order, so tasks are listed by entry point rather than in a table with call rates.
  • Interrupts: crank synchronisation, rpm calculation, low-level CAN reception. The visible code contains no reti at all.
  • The internals of ROM routines. Interpolation, PI controllers, filters and fault reporting are visible only through their arguments and results.
  • The immobilizer check, which is also in ROM.
